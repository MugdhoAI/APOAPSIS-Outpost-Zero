## 1. The challenge in plain language

NASA's challenge asks teams to build an interactive game or app where students run a lunar or Martian outpost. Players must balance competing systems such as life support, radiation protection, electrical power, and food production. The educational objective is to make the engineering trade-offs understandable and engaging: a decision that improves one system may consume resources or create risk elsewhere.

**The problem is not “make a space game.”** It is “teach students why keeping an outpost alive requires connected decisions under resource constraints.” A beautiful space-themed website with no meaningful decisions would not solve the challenge well.

Official challenge: [Build a Junior Astronaut Mission Trainer](https://www.spaceappschallenge.org/2026/challenges/junior-astronaut-mission-trainer/)

## 3. What APOAPSIS should build

### Candidate product: **Outpost Zero**

A browser game in which students try to keep a small lunar outpost operating through **five mission cycles**. Every cycle presents a decision or incident. The player chooses a response, sees the resource bars change, and gets a short explanation of the trade-off.

The proposed scope is deliberately small enough for three people in one hackathon. At the start of the event, compare it with the complete challenge statement and adapt if its requirements or required datasets point elsewhere.

### Core player loop

1. **Briefing:** explain the crew's goal, starting resources, and the fact that the model is a simplified learning simulation.
2. **Check the outpost:** show the current power, water, oxygen, food, radiation-protection level, and crew status.
3. **Make a decision:** present two or three meaningful actions—such as improve energy supply, conserve water, repair life support, grow food, or improve shielding.
4. **Reveal the consequence:** update the resource bars and explain what improved, what was consumed, and why.
5. **Handle an incident:** show a short scenario such as reduced solar power, a life-support fault, or a radiation alert. Do not present invented probabilities as real NASA forecasts.
6. **Repeat:** continue for five cycles, with a clear win/struggle/failure state.
7. **Mission debrief:** show the final status, the choices made, the most consequential trade-off, and one or two science lessons linked to NASA sources. Let the student restart and try a different strategy.

### The minimum viable product (MVP)

Finish these before adding features:

- One responsive web app that runs in a normal browser.
- One scenario: a **lunar outpost**, not both Moon and Mars. The second environment is a stretch goal only after the lunar version is complete.
- A resource dashboard with visible numerical values and bars.
- At least four distinct decisions with real trade-offs.
- A turn/mission-cycle loop and at least three incident types.
- Consequences that are internally consistent and reproducible enough to explain.
- Win, failure, and replay states.
- A mission debrief showing the player's choices and explaining why they mattered.
- An accessible **NASA Sources & Model Notes** panel.
- A public demo URL and public source repository.

### The feature that can distinguish the project

**Make the trade-off explain itself.** After every decision, show a short “Why this mattered” note. For example: a greenhouse improves future food supply but consumes power and water now; additional shielding reduces risk but diverts limited resources from other systems. Link these explanations to NASA references.

That explanation layer is more valuable than adding an AI chatbot. It connects the gameplay directly to the educational purpose and makes the scientific basis visible to judges.

### Avoid these scope traps

Do not start with a 3D environment, multiplayer, login/accounts, real-time backend, live API integrations, a custom large language model, complex orbital physics, or both Moon and Mars. None is necessary to demonstrate the central learning objective. A polished 2D interface with meaningful decisions is a stronger submission than a large, unfinished simulation.

## 5. Suggested technology stack

Use familiar, low-risk web technology rather than a complicated game engine:

- **Frontend:** React + TypeScript + Vite.
- **Styling:** plain CSS or a small existing styling approach the team already knows.
- **Game logic:** a small, separate TypeScript module with deterministic state updates.
- **Testing:** a few unit tests for resource changes and win/loss conditions, plus manual browser testing.
- **Hosting:** whichever of Netlify or Vercel the team can deploy to reliably; a public static host is sufficient.
- **Source control:** public GitHub repository, with a README and a suitable open-source licence for original code.

This is a recommendation, not an official event requirement. If the team is substantially faster with another stack, use that. Do not add a database, external AI API, or backend unless a real requirement justifies it.

### A basic architecture

- `src/game/types.ts` — types for game state, actions, events, and outcomes.
- `src/game/engine.ts` — resource consumption, action effects, event effects, scoring, and end conditions.
- `src/game/content.ts` — decision/event text and source references.
- `src/components/ResourcePanel.tsx` — resource levels.
- `src/components/DecisionCard.tsx` — action choices and trade-off text.
- `src/components/MissionDebrief.tsx` — outcome and learning notes.
- `src/App.tsx` and CSS — screens, layout, and overall interaction.

Keep the game logic separate from the presentation. That makes it easier to test and stops a UI edit from accidentally breaking the simulation.

## 11. How to compete effectively

The 2026 resources page and final judging guide are the authority for the actual rubric. Recent Space Apps judging frameworks use **Impact, Creativity, Validity, Relevance, and Presentation**. Treat these as useful design goals, then verify the official 2026 criteria before submission.

### Impact

- Explain who learns from the game and what they learn.
- Keep the game usable for young learners without assuming knowledge of space engineering.
- Show a real educational outcome: the player can explain why a decision protected one resource but weakened another.

### Creativity

- Make consequences visible and interactive rather than turning the game into a quiz or static infographic.
- Use the mission debrief and decision history as the signature feature.
- Avoid expensive visual features that don't improve learning.

### Validity

- Tie key mechanics to traceable NASA references or required datasets.
- Distinguish facts from assumptions and game balancing values.
- Never claim to predict actual lunar mission survival, dose, or engineering performance.
- Test that the simulation is logically consistent: resources cannot go below/above their intended bounds without an explanation, and choices must have the effects shown in the UI.

### Relevance

- Demonstrate the outpost-management decision loop directly.
- Give the user control over decisions and show outcomes.
- Finish the core requirements; a functioning small game is better than a collection of unfinished features.

### Presentation

- Make the initial screen explain the goal in one sentence.
- Make the central decision and its effect obvious within a few seconds.
- Keep the public site, README, source list, and 30-second video consistent with the actual implementation.
- Write the project page in clear English and explain how the project responds to the chosen challenge.

### The competitive advantage

The strongest differentiator is **scientifically grounded decisions explained through play**. Show judges a complete decision, not only the landing page: the player has a problem, considers trade-offs, acts, sees the resources change, and learns from the result. This is more persuasive than saying the project uses AI. Do not add AI unless it delivers a specific, testable learning benefit within the available time.

## 13. Fallback plan if things break

- **If Codex quota runs out:** stop prompting for large rewrites. Divide the remaining work into manual fixes and use another model for targeted debugging or review. Keep the simplest running version.
- **If the deployment fails:** test the production build locally, remove unnecessary dependencies, and use the hosting platform the team already knows. Do not switch stacks late.
- **If the NASA data integration is taking too long:** implement the smallest defensible connection to a verified NASA source, make its effect visible, document the limitation, and cite it. Never fabricate data or pretend a static NASA fact is a live dataset.
- **If the game is unfinished halfway through Day 2:** freeze the feature set and finish the loop, tests, sources, demo, and submission. Drop Mars mode, animation polish, sound, leaderboards, and anything else nonessential.
- **If the video is difficult to produce:** record the browser demo with narration or captions; avoid elaborate editing. A clear view of a working feature is the priority.
